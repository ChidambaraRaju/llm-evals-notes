    01
    Motivation

    Why LLM Evals

    Why “it seems to work” is not good enough, and why testing an LLM app is harder than testing ordinary software.

    1.1Vibe testing

    Definition · Vibe testing

    Trying an LLM app with a few prompts and judging it by feel.

    FlawVibe testingA real eval
    InformalWhatever questions come to mindA fixed, written set of test inputs
    SubjectiveNo metric — “felt good”Explicit criteria and a score
    Not repeatableCannot test v2 the way you tested v1Same procedure every run, so versions compare
    • Fine for a personal project; not for anything production-grade.
    • Building (LangChain, RAG, agents) answers how do I make it? Evals answer is it good enough to ship?
    • Standard interview question: “How do you evaluate your RAG app / agent?”

    1.2What happens when untested AI ships

    Same pattern each time: build → vibe test → deploy → incident.

    CaseWhat happenedFailureOutcome
    Air CanadaChatbot invented a bereavement-fare policy: “book now, claim the refund later”HallucinationTribunal: the company owns what its chatbot says. Paid the customer.
    Chevrolet dealerUser got the bot to agree with everything, then “bought” a car for $1JailbreakViral screenshots, reputational hit
    Mata v. AviancaLawyer filed ChatGPT-fabricated case citations without checkingHallucination~$5,000 fine

    1.3Why evaluating LLM apps is hard

    Traditional softwareLLM application
    OutputDeterministic — 2 + 2 is always 4Probabilistic — many differently worded answers, none wrong, so no single expected output
    What you checkOne thing: correctnessMany: factuality, completeness, tone, groundedness, latency, cost — and the list changes per app

    An app can look fine on the prompts you tried and fail on one you never imagined. The fix is evaluation that is systematic, repeatable and criteria-driven.

    Takeaway

    An AI app makes promises on your behalf. Evals are how you find out what it will say before a customer or a judge does.

    02
    Foundations

    What Is an Eval — Model vs Application

    The definition of an eval, and the two different things it can target.

    2.1The definition

    Definition · LLM evals

    Systematic, repeatable tests used to judge an LLM or an LLM-powered system against clear criteria.

    PropertyMeans
    SystematicA proper dataset that deliberately covers edge cases — e.g. 100 real user chats, not five questions off the top of your head
    RepeatableChange the prompt, model, retriever or chunking and still evaluate exactly the same way, so v1 and v2 scores compare
    Clear criteria“Good” is written down in advance: correct, simple, from our content, safe

    Without criteria you are vibe testing. With criteria you are evaluating.

    2.2An eval is not a metric

    Coming from classical ML, “evaluation” sounds like accuracy / precision / recall. Here the eval is the entire testing setup; the metric is only its output.

    DecisionQuestionExample
    WhatWhich part is under test?The retriever of a RAG bot
    CriteriaWhat does “good” mean?Retrieval accuracy
    DatasetWhich inputs?A prepared test set
    WhenAt what stage?Offline, or in production
    ToolWhat runs and scores it?e.g. RAGAS

    The goal is a decision, not a score: can this model do my task · is it good enough to ship · did prompt v2 beat v1 · is the answer grounded · is it safe · is latency under control.

    2.3Two targets: the model, or the application

    Model evalsApplication evals
    Question“Can the model do this?”“Does our product work?”
    TargetThe LLM on its ownThe whole system, or one component of it
    Measured withPublic benchmarks (MMLU, GSM8K, SWE-bench…)Your data and your criteria
    Who runs themFrontier labs and third partiesYou
    Your jobLiteracy — read benchmarks well enough to choose a modelBuild them hands-on (the main subject of the series)
    • The LLM is just one component. Around it: system prompt, tools & APIs, orchestration, guardrails, output parsers, memory, retrieval (embeddings, vector DB), monitoring. Model evals say nothing about whether those work.
    • Smartphone analogy: the chip maker benchmarks the processor; the phone maker still has to test the camera, OS and battery.
    • Application evals run at two levels: system (final response, latency, cost) and component (retriever, embedding model, re-ranker) — the second tells you where a problem lives.
    • “Model evals” / “application evals” are teaching labels. Industry says “LLM evals” for both and usually means the application kind.
    Takeaway

    “Is this a good model?” is answered by benchmarks someone else ran. “Is my application good?” is answered only by evals you build yourself.

    03
    Process

    The Evaluation Workflow, End to End

    The eleven-step loop used to evaluate any LLM application, on the simplest possible example.

    3.1The workflow

    Example: an email router at Zomato — one LLM and one prompt classify each customer email as billing, technical or general and route it to the matching team.

    #StepIn the email router
    1Task & targetTarget: the whole system. Task: classification.
    2Success criteriaCorrect classification, measured by accuracy
    3Golden datasetInput + hand-labelled correct answer, 50–500 rows, ideally real past emails. The most important step.
    4Eval methodWho scores: code, human or LLM. Here a few lines of Python.
    5RunSend every row through the app
    6EvaluateCompare with labels: 80 of 100 correct = 80%
    7AnalyseRead the failures: is the prompt confusing billing with technical, or is the model too weak?
    8ImproveFix the prompt or swap the model — the system, not only the model
    9IterateRe-run on the same dataset: prompt fix → 90%, stronger LLM → 95%
    10DeployWhen the score is good enough
    11MonitorThe downstream team flags misrouted emails → added to the golden dataset → loop again

    3.2Who does the scoring

    EvaluatorUse whenCatch
    CodeOutput is a label or exactly checkable valueCannot judge meaning in free text
    HumanLong free text that needs judgementExpensive every round
    Another LLMFree text at volumeMust itself be verified (Chapter 05)

    3.3Things to remember

    • 80 → 90 → 95 only means “better” because the dataset and scoring stayed fixed while the system changed. That is why evals must be repeatable.
    • Production has no gold labels, so some process has to surface failures (here: the team that received the wrong email).
    • The outer loop runs for as long as the system is live; the dataset gets richer with every failure.
    • One application usually has several evals — for a RAG app: retriever, embedding model, the whole workflow, latency. Each is its own pass through this workflow.
    Takeaway

    Evals are a loop, not a gate: target → criteria → golden data → method → run → score → analyse → improve → repeat. Production failures are tomorrow’s test cases.

    04
    Failure anatomy

    Why One Pipeline Is Never Enough

    One application needs many evals, for two reasons: many places to fail, and many ways to fail at each.

    4.1Reason one — three levels of failure points

    LevelWhat can failWhy the level below is not enough
    ComponentOne part: system prompt, retriever, re-ranker, query rewriter, embedding model, output parser, tool selector, memory, guardrails—
    WorkflowThe interaction between parts: a RAG, agent or multi-turn chat workflowParts that are each correct can combine into a wrong result
    ApplicationThe product as the user meets it: total latency, cost per query, time to first tokenA correct workflow can still be too slow or costly to ship
    Both components pass — the answer is still wrong

    “How long is the ML course?” The retriever (k = 5) returns the right document, ML: 8 weeks, in fifth place. The generator leans on the top documents, one of which says Python: 6 weeks, and answers “6 weeks”.

    • Retriever eval: pass — the right doc is inside the top 5.
    • Generator eval: pass — it used only its context.
    • Only a workflow-level eval sees the failure. Fix: add a re-ranker.
    • And if everything is right but takes 10 s per answer, only an application-level eval catches that.
    Definition · Faithfulness (groundedness)

    The answer is built only from the context it was given — no facts added from anywhere else.

    • Context “3 weeks” → “The ML course runs for 3 weeks” is faithful; adding “…you can also buy the 4-week Python course” is not.

    4.2Reason two — three risk categories

    At each failure point more than one thing can be wrong: quality (does it do the job?), safety (can it cause harm?), operations (fast, cheap, reliable?).

    4.3The risk catalogue

    CategoryApplies toRisks
    QualityAny LLM appCorrectness · relevance · completeness · instruction following
    RAGContext relevance · retriever recall · groundedness / faithfulness · citation accuracy
    AgentsTool selection · parameter correctness · task completion · error recovery
    Multi-turn chatContext retention · clarification behaviour (asks instead of guessing)
    SafetyAllToxicity · harmful content · bias · PII leakage · prompt injection & jailbreak resistance
    OperationsAllLatency · cost per request · token efficiency · error rate · latency under load
    Takeaway

    One score cannot represent a system. Evals = where it can fail (component, workflow, application) × how it can fail (quality, safety, operations).

    05
    Methods

    How to Score: Eval Methods & LLM-as-a-Judge

    Who actually runs an eval pipeline — a program, a person, or another LLM — and how to trust the third.

    5.1The three methods

    An eval method is who executes the pipeline and produces the score. Building the golden dataset is a separate activity, nearly always human.

    ProgrammaticLLM-as-a-JudgeHuman
    Also calledDeterministicModel-graded / LLM-graded—
    Handles nuanceNo — exactly checkable outputs onlyYesYes, best of all
    Cost at scaleNegligibleA fraction of human costHigh, paid per item
    TrustTotal, for what it can checkOnly after verifying against humansHighest
    Example hereRetriever → Recall@KUPSC answer grader → MAEChatbot helpfulness → 1–5 rubric
    Choosing

    Code if code can check it. Humans if the volume is small enough to afford. Otherwise an LLM judge — which is why most eval pipelines today are model-graded.

    5.2Programmatic: Recall@K

    Definition · Recall@K

    Of all the relevant documents that exist, how many did the retriever return in its top K?

    • Recall@K = relevant docs retrieved in top K ÷ relevant docs that exist · ideal is 100%
    • Gold docs {1001, 1003}, top 5 contains only 1001 → 1 / 2 = 50%. Average over all questions → e.g. Recall@5 = 67%.
    • Dataset: 50–100 likely questions; a human expert records which document IDs hold each answer.
    • Run: send questions to the retriever only, compare returned IDs with gold IDs.
    • Levers: better embedding model · query expansion · larger K · re-ranking.
    • Recall is one aspect of relevancy. The others: precision (how many fetched docs were useless?) and ranking (did the best land on top?).

    5.3Human: helpfulness

    • No standard metric for helpfulness, so you write a rubric: 5 = accurate, complete, right tone · 3 = partially helpful · 1 = not helpful.
    • The dataset is questions only — no gold answers.
    • Use more than one grader. Repeated disagreement (2 vs 4) means the rubric is ambiguous, not the chatbot.
    Five forms of human evaluation
    FormWhat happens
    Direct gradingScore outputs against a rubric
    Red teamingDeliberately attack the system to find where it breaks
    A/B testingTwo versions in production; real users are the evaluators
    Golden dataset & rubric creationLabelling the right answer is itself evaluation
    Human-in-the-loopCases too grey for code or an LLM judge go to a person

    5.4LLM-as-a-Judge: the UPSC grader

    App: a platform that grades subjective UPSC Mains answers with an LLM instead of paid experts. Criterion: it grades the way a human expert would.

    • Rubric (not the dataset): per question, the dimensions a good answer must cover — e.g. addresses both concepts · explains the link · gives mechanisms · cites examples · balanced conclusion.
    • Golden dataset: 50–100 real student answers, each with the human expert’s marks.
    The judge prompt
    PartContent
    Role“You are grading a UPSC Mains answer against an evaluation rubric.”
    InputsQuestion · maximum marks · the rubric for that question · the student’s answer
    RulesPer dimension, decide if it is genuinely addressed. Do not reward verbosity, keyword stuffing or unsupported confidence. Reward structure, examples, balance.
    OutputDimensions addressed · total marks · one-sentence justification
    Trust, but verify · MAE

    Mean absolute error = average of |human marks − judge marks| over the golden dataset.

    • Human 13 / judge 12, 4 / 8, 8 / 8 … → (1 + 4 + 0 + …) ÷ 50 = 2.3: the judge is off by ±2.3 marks on average.
    • Push it towards 0 with a better LLM, a better prompt or a clearer rubric — re-measured on the same dataset.

    5.5Reference-based vs reference-free

    The test: does the golden dataset hold the correct answer for each row? Yes → reference-based. No, only a rubric → reference-free.

    ExampleDataset holdsType
    Retriever · programmaticQuestion + gold document IDsReference-based
    Helpfulness · humanQuestions onlyReference-free
    UPSC grader · LLM judgeAnswer + human marksReference-based

    The method does not determine the type: an LLM-judged eval can be reference-based, a human-graded one reference-free.

    Takeaway

    Code where you can, humans where you can afford them, an LLM judge for everything in between — and never trust the judge until its gap against human grades is close to zero.

    06
    Lifecycle

    Offline vs Online Evals

    Before release you test for correctness. After release you watch for normality. Neither replaces the other.

    6.1Offline evals

    Definition · Offline eval

    Any eval run on your application before deploying it, on a fixed golden dataset, to decide whether it is fit to deploy.

    Three jobs
    JobHow
    Release gateIn CI/CD: push → eval script runs on the golden set → score ≥ threshold (say 95%) → deploy; otherwise stop, notify, keep the old version
    Version comparisonTwo prompts / models / re-rankers / architectures: keep everything else identical, same eval, same dataset, higher score wins
    Regression testingScore per question type before and after a change; any category that drops is a regression

    Regression example: adding “be very polite” to fix cold refund answers made the bot soften a ₹19,500 price to “around ₹19,000”. A score going from 92 to 99 is only good if nothing else fell.

    6.2Why production still surprises you

    • Unanticipated inputs — Hinglish, half-questions, angry rants, prompt injections. Real users are a superset of your 200–500 test questions.
    • Emergent failures — only visible at scale: latency under a launch-day spike, a subtle bias across thousands of chats.
    • Drift — prices, policies and documents change; the golden dataset goes stale while offline scores still look good.

    Root cause: in production there is no golden dataset — no answer key.

    6.3Online evals

    Definition · Online eval

    Evaluating the system on live production traffic, after deployment, without an answer key.

    OfflineOnline
    WhenBefore deploymentAfter, continuously
    DataFixed golden datasetLive traffic
    Answer keyUsually yesNo
    AsksIs it correct?Is it normal?
    CatchesRegressionsDrift, surprises, emergent bugs
    Used forGating, version comparison, CIDrift detection, real-world performance
    CostFast, cheap, repeatableCostly at scale, hence sampling

    With no answer key, two routes to a quality signal:

    • Reference-free metrics — e.g. faithfulness: an LLM checks the answer against the retrieved context; no “correct answer” needed.
    • Proxies — compare against a baseline distribution, or use user feedback (a burst of thumbs-down).

    Baseline example: the UPSC grader’s weekly marks cluster near 500 for four weeks, then near 800. That does not prove it is wrong (maybe a strong batch) — it says something is different and someone should look.

    6.4Logging comes first

    Capture a structured, replayable record of every conversation turn.

    What to log
    • Identity — conversation, turn, user, session IDs, timestamp
    • Content — question, retrieved context, output
    • Operations — latency, tokens, cost, errors
    • Behaviour — thumbs, escalation, repeated rephrasing
    How it must behave
    • Non-blocking — adds no latency
    • Durable & queryable
    • Late signal attachment — a complaint a day later still links to the conversation ID
    • PII masked before storage

    6.5Two kinds of signals, two pipelines

    CapturedComputed
    WhatAlready present — just store itAn evaluator has to work it out
    ExamplesThumbs up/down · latency · cost · token usageFaithfulness · relevance · hallucination · toxicity · bias
    PipelineLog → dashboard → alertLog → sample → LLM judge → dashboard → alert
    • Dashboard: what matters is the aggregate over a time window, not one slow conversation.
    • Alerts: threshold crossed → Slack, email, PagerDuty, webhook.
    • Read against a baseline from offline evals: faithfulness baseline 0.85 → live 0.87 is fine, 0.75 fires the alert.
    • The online judge is reference-free: a stronger LLM shown the context, question and output, with a detailed rubric.

    6.6Stratified sampling

    Judging every conversation would roughly double the bill, so evaluate a sample — say 1,000 of 50,000 — and draw more heavily from risky categories rather than at random.

    • Sample heavily: thumbs-down · escalated or ended abruptly · user kept rephrasing · money topics (fees, refunds, admission).
    • Sample lightly: ordinary conversations · thumbs-up (probably fine — a signal, not a fact).

    6.7In LangSmith, and closing the loop

    StageLangSmith feature
    LoggingTracing
    DashboardMonitoring — latency, error rate, LLM calls, cost per window
    AlertingAlerts — “above X in the last 5 minutes” → Slack / PagerDuty / API
    EvaluatorEvaluators — LLM-judge templates: PII, prompt injection, toxicity, bias, hallucination, correctness, conciseness, agent trajectory
    Golden datasetDatasets & experiments
    • Same evaluator, one switch: run on traces → online; run on a dataset → offline.
    • Add to Dataset + an annotation queue turn a bad production trace into an offline test case.
    • The loop: offline pass → ship → online surfaces failures → annotate and add to the dataset → offline again → redeploy.

    Tools used from here on: LangSmith, DeepEval, Ragas.

    Takeaway

    Offline asks “is it correct?” before release; online asks “is it normal?” after. Logging is the spine, sampling keeps it affordable, and production failures feed the golden dataset.

    07
    Model evals & capabilities

    Evaluating the Model Itself

    How to pick a model with evidence, and the eight capabilities every benchmark targets.

    7.1What a model eval is, and why you need it

    Definition · Model eval

    A systematic process of measuring a model’s capabilities, behaviour, reliability and operational characteristics under controlled conditions.

    • Four uses for an AI engineer: choosing between models · judging whether to upgrade to a new release · knowing how safe it is · deciding API vs self-hosted.
    • LLMs are general-purpose, so no single eval covers them — there is no IQ score for models. Each capability gets its own eval.

    7.2The four steps

    1. Decide the capability — reasoning, coding, safety…
    2. Bring a test — a benchmark or a custom eval set.
    3. Run under a fixed protocol — same prompts and settings for every model, or scores cannot be compared.
    4. Score and interpret.
    BenchmarkCustom eval set
    WhatStandardised, shared test — same for every modelData you assemble from your actual task
    MeasuresGeneric capabilityFit for your application
    Answers“Which model is more capable in general?”“Which model suits my work?”

    7.3The Model A / Model B lesson

    Email router again. A tops every public benchmark; B is mid-table. Run both on 200–500 of your own labelled emails:

    Model A · largeModel B · small
    Price per million tokens~$15~$0.50
    Classification accuracy94%91%
    Urgency accuracy88%87%
    Cost per 1,000 emails$6.00< $0.21
    Latency per request4.1 s0.9 s

    Give up 3 points of accuracy; cost falls ~28×, latency ~4.5×. Ship B. Benchmarks tell you about generic capability; only a custom eval tells you about fit.

    7.4The eight core capabilities

    Every benchmark you meet targets one of these.

    #CapabilityWhat it coversBenchmark
    1Knowledge & reasoningFactual recall across subjects + multi-step logical reasoning. Read as “how intelligent is it”.MMLU (57 subjects)
    2Coding & software engineeringFunction generation, bug fixing, multi-file long-horizon tasks, command line, API calling. Economically the most important.HumanEval · SWE-bench
    3MathematicsGrade school → olympiad → undergraduate → research-level problemsGSM8K
    4Long contextActually using very long inputs. Windows of 128k–1M are advertised, but quality drops as context grows.Needle-in-a-Haystack
    5Vision & multimodalUnderstanding images and videoMMMU
    6Agentic & tool useWeb browsing, structured tool calling, APIs, computer use — acting, not just talkingfunction-calling suites
    7Safety & alignmentHarmful content, resistance to adversarial attacks, truthful vs sycophantic, cybersecurity skills—
    8Instruction followingObeys format, length and tone; asks a clarifying question when the instruction is ambiguousIFEval
    Takeaway

    Capability first, test second, fixed protocol third, interpretation last. The right model is the one that clears your bar at a cost and speed your product can live with.

    08
    Benchmarking

    Benchmarks: How They Work, and When Not to Trust Them

    What is inside a benchmark, how it is run, who runs it — and four reasons a published score deserves a pinch of salt.

    8.1Anatomy of a benchmark

    Definition · Benchmark

    A standardised test used to measure one particular capability of a model.

    The four parts — all specified in the benchmark’s research paper
    PartWhat it isIn GSM8K
    Dataset & taskQuestions plus the answer key~8,500 grade-school maths problems with solutions
    Run configurationThe conditions every model runs under8-shot · chain of thought · temperature ≈ 0 · no tools
    ScoringExtract the answer, compare with the keyPull out “72”, exact match → 1 or 0
    AggregationCombine per-question scoresMean of the 1s and 0s → e.g. 92%

    8.2Run configuration

    Fixed for fairness: scores from different conditions cannot be compared.

    SettingThe choice
    Zero-shot vs few-shotQuestion alone, or with solved examples first. Few-shot raises scores.
    Chain of thought vs directStep by step, or the answer straight away. Direct makes mistakes likelier.
    Temperature≈ 0, so answers do not vary from run to run
    Max tokensSame for every model. Too low cuts reasoning off before the answer.
    ToolsWeb search or a code interpreter would trivialise many tests. Some need them (SWE-bench).
    AttemptsPass@1 — one try, strict · Pass@k — any of k correct, lenient · Majority@k — the most common of k answers
    Reading habit

    “82% on benchmark X” — was that Pass@1, Pass@k or Majority@k? The same model gets a different number under each.

    8.3Scoring and aggregation

    • Extraction: “The answer is 72”, “72” and “seventy-two” must all become 72 — via structured output or regex. Harder than it sounds.
    • Comparison: closed-ended → exact match. Open-ended → an LLM judge or a human.
    • Aggregation: usually a plain mean. When sub-sets differ in size (MMLU’s 57 subjects), a weighted mean.

    8.4Running one: the loop and the harness

    results = [] for item in dataset: prompt = build_prompt(item, few_shot=8) # as the paper says raw = model.generate(prompt, temperature=0, max_tokens=...) pred = extract_answer(raw) # "The answer is 72" -> 72 results.append(pred == item.answer) final_score = mean(results)
    Definition · Eval harness

    The code — almost always a library — that actually executes a model evaluation: all the plumbing around the loop.

    • Plumbing: robust extraction · scoring as the paper defines · batching · retries · rate limits.
    • Analogy: the benchmark is the exam paper; the harness is the examination administration.
    • Libraries: lm-evaluation-harness (EleutherAI, the industry standard) · Inspect · HELM · DeepEval (aimed more at application evals).
    pip install -q "lm_eval[api]" # needs OPENAI_API_KEY in the environment lm-eval run \ --model openai-chat-completions \ --model_args "model=gpt-5.6-luna,num_concurrent=5,max_retries=5" \ --tasks gsm8k_cot \ --num_fewshot 8 \ --apply_chat_template \ --limit 20 \ --output_path ./gsm8k_results \ --log_samples

    gsm8k_cot = GSM8K with chain of thought. --limit 20 is a smoke test — remove it for a real run. --log_samples writes one JSON record per question. With the limit: 18 of 20 correct = 90%, for about ₹3–4; the full ~8,500 questions would cost around ₹2,300.

    8.5Who runs benchmarks — and how far to trust each

    WhoWhyHow to read their numbers
    Frontier labsDevelopment checkpoints, release gating, marketingA ceiling, not an expectation: self-run, most favourable settings, cherry-picked
    Third parties
    leaderboards    		Evaluation is their productThe most reliable: same conditions for all, published method, plus cost and latency
    YouBenchmarks are public, harnesses are freeClosest to your reality

    The mileage rule: a lab’s number is like a car’s advertised mileage. If the answer to “who ran this?” is “we did, in our own settings”, do not choose your model on it alone.

    8.6Four reasons for a pinch of salt

    PitfallWhat goes wrongWhat to do or know
    ContaminationPublic test data ended up in the model’s training data, so a high score may be memoryPrefer private benchmarks (data unpublished) and dynamic ones (refreshed on a schedule)
    SaturationEvery model scores near the top; the benchmark no longer separates themGSM8K, MMLU and SWE-bench are saturated. Life cycle: new → improving → saturated → retired.
    Configuration gamingLabs choose settings that flatter their own modelConfig alone moves a score 5–10%; self-reported scores are not comparable across labs
    AggregationOne average hides weak sub-scores (strong physics, weak economics)Ask for the breakdown that matches your use case
    Takeaway

    A benchmark is a dataset, a run configuration, a scoring rule and an aggregation rule, run in a loop by a harness. Its score is evidence, not a verdict: ask who ran it, under what settings, and what the average hides.

    09
    Model selection

    Leaderboards and Custom Evals: Choosing the Model

    Use leaderboards to filter the field, then your own eval on your own data to decide — worked end to end on one case study.

    9.1Leaderboards

    Definition · LLM leaderboard

    A public ranking table showing how different LLMs perform on a common set of evaluations.

    • The benchmark is the exam; the leaderboard is where the results are published.
    • Why they are useful: a common reference · third-party trust · selection without running hundreds of models yourself · clustering reveals saturation · discovery of cheaper models further down.
    Four types
    TypeWhat it ranks onExampleNote
    Benchmark-specificOne benchmarkHumanity’s Last ExamNarrow — least useful
    Multi-benchmarkMany benchmarks combined, plus cost, latency, speed, context windowLiveBench · Artificial AnalysisMost useful
    Human-preferenceBlind votes between two anonymous modelsLM ArenaPopular, but preferred ≠ better
    Application-specificOne domain or jobBerkeley Function-CallingUse when your app lives in that domain

    9.2Seven reasons not to trust one blindly

    #ReasonWhat goes wrong
    1Scores may not transferBenchmark data is clean; real requests are ambiguous, incomplete and company-specific
    2ContaminationLeaked benchmark → inflated score
    3Over-optimising for the boardLabs tune to top it — e.g. flattering, nicely formatted answers for a voted arena
    4Hidden composite choicesWhich benchmarks, how normalised, what weights? Prefer transparent boards.
    5Small gaps are not real84.3 at rank 3 and 84.1 at rank 5 are the same level
    6Human-preference biasLonger, more confident, better-formatted answers win votes
    7Stale or self-reportedNewest models missing; some entries submitted by the company itself
    Goodhart’s law

    “When a measure becomes a target, it ceases to be a good measure.”

    9.3How to read a leaderboard

    1. Write requirements first — task, latency, cost, context, deployment constraints. This stops rank-1 bias.
    2. Pick the board that matches the job (table below).
    3. Read the footnotes — what is scored and how · who ran it · inference budget · reasoning on or off · dataset age and refresh · private test set · saturation · confidence intervals · composite weights.
    4. Shortlist 3–5 candidates, not a winner.
    5. Run your own eval on them — the step that decides.
    BuildingLook at
    An agentAn agent / function-calling leaderboard
    A chatbotAn LM Arena-style board
    RAGMTEB — it ranks embedding models
    Anything on a tight budgetArtificial Analysis · Vellum — speed and cost stated
    The one line to remember

    A leaderboard is a filtering tool, not a decision tool.

    9.4Case study — text-to-SQL, stage 1: requirements

    “Ask Cricinfo”: a fan types a cricket stats question → the prompt (system text + database schema + question) goes to an LLM → the LLM writes SQL → the SQL runs on the database → the result is shown. Which LLM?

    RequirementAnswerWhy

    9.5Costing a model

    cost_per_query = input_tokens × input_price / 1,000,000 + output_tokens × output_price / 1,000,000 monthly_cost = cost_per_query × queries_per_day × 30 × (USD → INR)
    Worked number · the top model at $10 in / $50 out per million

    Workload: ~400 input tokens, ~100 output tokens, ~50,000 queries a day.

    • Per query: 400 × 10 ⁄ 1M + 100 × 50 ⁄ 1M = $0.009
    • Per month: 0.009 × 50,000 × 30 = $13,500 ≈ ₹12.8 lakh at ₹95 — over four times the ceiling.
    • Output tokens are always priced higher than input tokens.
    • Blended price: one figure at a stated input : output ratio. At 4 : 1 → (4 × 10 + 1 × 50) ÷ 5 = $18. Always check the ratio — it differs between leaderboards.
    • Shortcut for this workload: monthly ₹ ≈ blended price × 71,250, so a ₹3 lakh ceiling means a blended price ≤ ~$4.2.

    9.6Prompt caching

    Definition · Prompt caching

    The provider stores the repeated prefix of your prompt and charges far less for it on every later call that reuses it.

    Rate (per million tokens)PriceWhen
    Normal input$10No caching
    5-minute cache write$12.50First call — dearer than normal input
    1-hour cache write$20First call, longer-lived cache
    Cache hit$1Every later call while the cache is alive
    • High traffic → 5-minute cache (something always arrives in time). Low traffic → 1-hour cache.
    • Here the system text + schema (~350 of 400 tokens) repeat on every call: input cost falls ~90%, the bill drops to roughly ₹7–8 lakh — still over budget.
    • Helps only when a large prefix repeats. In RAG most of the prompt is retrieved context that changes per query.
    • Under the hood: KV caching of the attention keys and values.

    9.7Stage 2 — shortlist from a leaderboard

    • Text-to-SQL boards (BIRD-SQL, Spider, LiveSQLBench) were unusable: stale, or listing fine-tuned models and whole systems rather than base models.
    • Fallback: coding ability as a proxy — the coding board on llm-stats.com (146 models, with cost and speed).
    1. Compute every model’s monthly cost from its blended price.
    2. Drop everything over the ceiling (a hard filter).
    3. Min-max normalise coding rating and output speed to 0–1.
    4. Combine with weights, sort, take the top ten, remove what you cannot use.
    norm(x) = (x − min) / (max − min) score = 0.9 × norm(coding_rating) + 0.1 × norm(output_speed)

    Speed gets only 10% because the output is one ~100-token query — even a slow model prints that in about a second. The weights are a judgement call per application. Tested: GPT-5.6 Terra, Kimi K3, Grok 4.5, Claude Sonnet 5, MiniMax M3.

    9.8Stage 3 — golden dataset and execution accuracy

    Definition · Golden dataset (text-to-SQL)

    Questions, each paired with the correct SQL — written by an analyst and validated by running it.

    • Each row: question · gold SQL · gold result · difficulty · expected row count · whether row order matters.
    • Build it: representative of real questions · varied (joins, sub-queries, window functions) · human-verified · 50–500 rows (each one is a call per candidate) · never finished.
    • A gold query that runs is not proven right — a human must own the dataset.
    Definition · Execution accuracy

    The share of questions where the generated query, when executed, returns the same result as the gold query.

    • Never compare SQL text: many different queries return the same table.

    What “same result” means, in order:

    1. The query must run — errors are logged separately as sql_error.
    2. Row counts must match.
    3. Canonicalise values — 2.0 = 2, round floats, trim strings, unify empties.
    4. Ignore column names — runs vs total_runs.
    5. Sort rows before comparing — unless the question is order-sensitive.
    6. Allow one extra or missing column if the smaller table’s values all appear in the larger.
    for model in candidates: correct = 0 for row in golden_dataset: sql = strip_markdown(model.generate(system + schema + row.question)) # temp 0 table = run_on_db(sql) # None if the SQL errors out correct += same_result(table, row.gold_result, row.order_sensitive) accuracy[model] = correct / len(golden_dataset)

    Reference-based and programmatic — no judge model. Smoke-test one question on one model before the full run. OpenRouter gives one API and one key for all five providers; the whole run cost about $5. Demo data: IPL 2021–24 in SQLite (matches, deliveries), 20 deliberately hard questions. Code: campusx-official/llm-sql-eval.

    Caveats to state with any such result:

    • 20 questions is too few — one answer is worth 5 points.
    • Run it several times and average.
    • Measure latency in the eval instead of judging by eye.
    • How much accuracy is worth paying for depends on the stakes (medical vs consumer).
    Takeaway

    Requirements first, then a leaderboard to filter, then your own eval to decide. The leaderboard tells you who is worth testing; only your data and your scoring rule tell you who to build on.
